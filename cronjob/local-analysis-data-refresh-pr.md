# Local analysis refresh job

This is the self-contained prompt used by the scheduled local tier-list refresh. The job runs on the maintainer's analysis machine and publishes only reviewed generated outputs.

## Schedule

Run on Sunday, Tuesday, Thursday, and Saturday at 21:00 UTC.

## Prerequisite

This job publishes premium data to Firestore, so the analysis machine needs Application Default Credentials for the project before step 10 runs. The publisher identifies the canonical Git remote by its GitHub repository URL (`PocketDecks/pokemon-tcg-pocket-tier-list`) and uses that remote's `main` as the comparison baseline. Its local alias can vary between checkouts.

If the publish or verify step fails, report the exact refusal and stop. The published version document is written last, so readers never see a half-written version. Publishing before the merge is safe: cleanup keeps the newest five versions and protects the versions referenced by canonical `main`, the deployed version document on the site, and every open pull request targeting canonical `main`, including pull requests from forks. If any retention source cannot be read, publishing may proceed but deletes nothing, and the refusal names the source that could not be read.

The premium publication lock uses a Firestore transaction before listing existing versions. A competing run refuses and must stop with the lock details. A crash leaves the lock in place without automatic expiry. Before a person removes it, they must confirm the lock owner at the recorded host and process ID is gone; otherwise stop and report the lock.

## Prompt

Run the Pokemon Pocket tier-list refresh and publish a review branch only when the result passes every check.

Repository: the checked-out `pokemon-tcg-pocket-tier-list` repository.

1. From `analysis/`, run `yarn.cmd refresh:outputs recover`. It restores the generated files to their baseline from the start of the run and repairs recognised writer sidecars only when their backups or owner proofs match that baseline. It does not recover `analysis/data/`. If recovery reports an error, leaves `public/og/deck-stage-*` or `public/og/deck.previous`, or any generated output is still dirty, stop and report the exact paths. Untracked tool directories do not stop recovery; every other untracked file and any change to a tracked file does. Then fetch and update `main` from the remote whose GitHub URL resolves to the canonical repository above; the remote alias can vary between checkouts. When `main` is not checked out, run `git fetch <remote> refs/heads/main:refs/remotes/<remote>/main` then `git branch -f main refs/remotes/<remote>/main`; when it is checked out, run `git pull --ff-only <remote> main` instead. Never check out or reset `main` from this job, and stop if either command fails.
2. Create a dated branch named `automated/pipeline-update-YYYY-MM-DD` from the current `main` branch. Reuse the dated branch only when it contains no human commits: compare the local branch and its remote counterpart with `git log --format='%h %an %s' main..<branch>` and `git log --format='%h %an %s' main..refs/remotes/<remote>/<branch>`, and treat every commit that is not reachable from canonical `main` as human unless its subject is `chore(data): refresh tier-list snapshot` and its author is the automation identity. If any human commit is present, stop, report the branch and the commit list, and let a person decide; never reset, delete, rebase or force-push that branch. Stop if branch creation or checkout fails.
3. From `analysis/`, run `yarn.cmd refresh:outputs begin`. Stop if it fails. Then run `yarn.cmd sync-pairings`. Run `yarn.cmd refresh:outputs checkpoint` even on failure, then stop on a non-zero exit.
4. From `analysis/`, run `yarn.cmd golden:generate`, checkpoint its outputs even on failure, then stop on a non-zero exit.
5. Run `yarn.cmd store:verify` from `analysis/` and continue only when it exits 0. It now also reads `processed-tournaments.json`, its staging sidecars, and every shard entry, so a batch killed between the manifest and processed-tournaments renames is reported here instead of surfacing later as a duplicate-deck refusal. Recovery ran before fetch and the worktree check in step 1. If verification fails, stop. Before any human repair, copy the full `analysis/data/` directory, including `decks/`, `processed-tournaments.json` and any sidecars, to `analysis/data-backup/YYYY-MM-DD/`, then ask a person to review it. Never delete or restore raw-store files automatically.
6. From `analysis/`, run `yarn.cmd download`. The downloader commits the deck store a batch at a time, so a run that fails with a thrown error keeps the batches that finished: every deck in the store belongs to a tournament in `processed-tournaments.json`, and every tournament listed there has been processed, whether or not it produced usable decks. A run that fails with a thrown error may be rerun from those batches without duplicating a deck. A killed run can leave the shard and manifest on the new batch while `processed-tournaments.json` still holds the old one; `yarn.cmd store:verify` now reports that state and its staging sidecars. If it does, or if a rerun refuses with `Deck ... already exists in shard`, do not rerun again: apply the backup-and-stop rule in step 5, report the exact refusal, and let a person reconcile the batch. Do not rerun inside the same run after recovery: recovery removes the refresh journal, so the first checkpoint of a rerun would fail. Start the next run again at step 1, create the journal with `yarn.cmd refresh:outputs begin` in step 3, and run `yarn.cmd store:verify` before `yarn.cmd download`. Partial output is not a reason to stop, because the store is the resume point. Stop on any non-zero exit and report the exact error.
7. From `analysis/`, run `yarn.cmd card-printings:generate`, then run `yarn.cmd start`. It runs `assertPublishable` before writing JSON. It commits JSON atomically, then commits OG images separately; the image commit can fail after JSON publication, in which case the rendered staging directory is kept and the refusal names its exact path. Checkpoint after each mutation even on non-zero exit, then stop on failure. From the repository root, run `node scripts/build-deck-archive.mjs`, `node scripts/generate-deck-hub-slugs.mjs`, then `node scripts/generate-deck-redirects.mjs`, checkpointing each command and stopping on its failure. From `analysis/`, run `yarn.cmd validate:refresh` (the script exists only in `analysis/package.json`) and stop on failure.
8. Run `yarn.cmd test` and `yarn.cmd typecheck` from `analysis/`. From the repository root, run `yarn.cmd typecheck`, `yarn.cmd lint`, `yarn.cmd test:ci`, and `yarn.cmd check:generated`. Stop at the first failure and report the command and first error.
9. Inspect `git status --short` and run `yarn.cmd refresh:outputs classify`. If the classifier prints no paths, run `yarn.cmd refresh:outputs recover`, report a silent day and stop. The classifier excludes `src/app/last-updated.ts` and includes ignored premium outputs; generated hub files count as output. Never stage `analysis/data/`. Stop on any non-zero exit and report the exact error.
10. From `analysis/`, run `yarn.cmd publish:premium --dry-run`, then `yarn.cmd publish:premium`, then `yarn.cmd verify:premium`. Stop on any non-zero exit and report the refusal.
11. Run `yarn.cmd refresh:outputs stage` from `analysis/`, then commit the staged outputs with `chore(data): refresh tier-list snapshot`. After a successful commit, run `yarn.cmd refresh:outputs finish`. Stop on any non-zero exit and report the command and first error; do not push a partial commit.
12. Push the dated branch to the repository's review remote and create or update one pull request against `main`. Use the title `chore(data): refresh tier-list snapshot`. The body must state the pairing-row count, ranked-archetype count, image parity, test results, and the published premium version (matching `public/data/data-version.json`). Check the title and body for EN-UK spelling and ensure the gate is applied before posting. Stop on any non-zero exit and report the command and first error. If the push succeeds but the pull request cannot be created, report the pushed branch and stop without republishing; the next run reuses that dated branch.
13. Read the pull request back after publishing. Verify that its head SHA equals the local commit and report the review URL plus the current check states. Stop on any non-zero exit and report the command and first error; stop and report immediately if the head SHA differs. Never merge and never push `main`.

## Freshness

Windows anchor on the newest data date, so stale raw data still fills each window and ranks archetypes. Score weights use that same data anchor. The trend series includes every calendar day with qualified games, so a day's decks appear in the run that first sees them and a run with no new data stays silent. The run clock still sets `LAST_UPDATED`. `assertPublishable` compares the newest qualified deck date with the run clock and refuses data older than `MAX_DATA_AGE_DAYS`; this freshness guard is implemented in code. The gate in `yarn.cmd start` runs before the new files are written and reads the free-window baselines from the working tree; `yarn.cmd validate:refresh` runs afterwards and reads both free and premium baselines from canonical `main`. They share the floor date source, ramp, ratio and release rule, but the validator does not repeat the gate's ranked, age, unmatched-bucket, slug or listing checks. A fresh checkout has no local snapshot for the version canonical `main` serves, so both log a first publish and skip only the previous-archetype-count ratio for the 30d and all windows; the configured floors still apply. `publish:premium` writes that snapshot.

## Recovery refusals

Step 1 fails closed and leaves the evidence in place; nothing is deleted before every check passes. Use these remedies before starting another run:

- `Refusing stale staging files`: `writeArtefacts` refuses to start when a target still has a `.tmp`, `.bak` or `.created` beside it, meaning the previous JSON write was killed partway. Confirm no refresh process is running, then remove the `.tmp`/`.bak`/`.created` and any leftover `.tmp.owner` for that target by hand (restore the target from its `.bak` first when the target is incomplete), then rerun the failing step. A `.tmp.owner` left with no `.tmp`/`.bak`/`.created` is now cleared automatically at the start of the next `writeArtefacts` write and needs no manual removal; the next write no longer stalls with no remedy.
- `unproven sidecar state`, `unproven created marker`, `unproven target`, `unowned backup`, `unverified completed write`: confirm no refresh process is running, inspect the named `.tmp`, `.bak` and `.created` files, remove only the ones you can account for, then rerun `yarn.cmd refresh:outputs recover`. When recovery refuses a completed write whose `.bak` still equals the baseline but the target already holds content the journal does not expect, restore the target from its `.bak` (or remove the target and the sidecars together) only after a person confirms the intent, then rerun recovery.
- `unproven atomic temporary` or `invalid atomic temporary proof`: a writer was killed. Confirm the pid in the filename is gone, remove the `.tmp` and `.tmp.owner` pair by hand, then rerun recovery. An owner proof with no temporary is removed automatically only when the target still matches its checkpoint; if the target changed too, recovery refuses with `unrecorded file changes` and those paths need human review. Recovery checks the pid with `process.kill(pid, 0)`, so a pid reused by an unrelated process after the writer died still looks alive and triggers `atomic writer is still active for <name>` even though no refresh holds it. In that case confirm no refresh process is running on this machine, delete the `.tmp` and `.tmp.owner` pair by hand, then rerun recovery; this job must not delete them automatically.
- `unrecorded file changes` or `unexpected file in <tree>`: a generated output changed outside a checkpoint, or a stray file sits in a generated tree. Report the paths and let a person decide; do not delete them to make recovery pass.
- `unowned OG staging directories`: a failed image swap after the JSON was published keeps `public/og/deck-stage-*` so the rendered set survives. Step 1 stops on purpose. A person must finish the swap from that directory or remove it after confirming the published images are correct; the job never deletes it.
- A writer that fell back to a direct write on Windows can leave the target, `.tmp`, `.tmp.owner` and `.bak` together. Recovery refuses that combination. Confirm no writer is running, compare the `.bak` bytes with the last published state, remove the sidecars by hand, then rerun recovery.
- `worktree changes without a journal`: recovery already removed the journal in an earlier run. Start a new run at step 1; do not call `begin` twice.
- `HEAD changed` or `commit does not match the run checkpoint`: the branch moved during the run. Report the commit and stop.

The journal is written to a temporary file and renamed into place, so a killed write leaves the previous journal intact. Sidecars are validated as a whole before any of them is removed.

## Failure rules

- Do not publish raw tournament data.
- Do not treat a failed download as a finished one. A run that failed with a thrown error keeps the completed batches and may be rerun once. A killed run needs the recovery in step 1, which removes the refresh journal, so start a new run at step 1, create a fresh journal with `yarn.cmd refresh:outputs begin` in step 3, and run `yarn.cmd store:verify` before `yarn.cmd download`; never rerun after recovery inside the same run. If store:verify reports an interrupted processed-tournaments batch, or a rerun refuses with `Deck ... already exists in shard`, stop, back up `analysis/data/` as step 5 requires, and ask a person to reconcile it; a blind rerun cannot fix that state.
- A download refused by the store lock may be retried once, after a few seconds, if the refusal says to retry. Any other refusal is stopped and reported, naming the holding pid, the claim file, or the lock file. A later run reclaims a lock or claim whose owner has gone. The exception is a claim or lock whose pid has been reused by an unrelated process: it still looks held and needs deleting by hand, which this job must not do, so stop and report it.
- Do not override a refusal from `yarn.cmd start`. Report the failures it prints.
- Do not open a second review for the same dated branch.
- A run is silent only when `yarn.cmd refresh:outputs classify` prints no paths. The classifier excludes `src/app/last-updated.ts` and counts ignored premium outputs.
