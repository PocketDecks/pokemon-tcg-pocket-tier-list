# Explanation: Advertising, premium and consent

The site is free to use, with advertising for visitors who consent to marketing. Premium access removes ads and lifts the data limits. Three subsystems cooperate to make that work: the ads layer under `src/ads/`, the premium check in `src/app/use-is-premium.ts` and `src/components/Premium.tsx`, and the consent layer under `src/consent/`. This page explains why each piece exists and how they interact. The routing and provider stack around them is covered in the frontend architecture reference.

## The two gates

Premium restricts two things.

The first is content volume. A free visitor gets matchups and movement for the ten highest-scoring decks of the 10-day and 20-day windows, and nothing deeper. On `/statistics` the matrix is limited to those ten decks and the movement lists show only decks that carry movement, with a note linking to the Premium page. On a deck page, a free visitor sees the strong and weak matchups of a top-10 deck and a Premium notice in place of both lists for any other deck. The 30-day and All Time toggles are locked for free users. Users with an active entitlement get the full matrix, every deck's matchups and movement, and the complete history.

The second is advertising itself. Free visitors see Google AdSense units: a sticky anchor bar along the bottom of every page, plus in-content units on individual routes. Premium users see none of it. Both gates hang off one hook, `useAdsState()`, which combines the master switch `ADS_ENABLED` in `adsConfig.ts`, premium status, marketing consent and page readiness into a single `showAds` decision. Placement components never make these calls themselves, so there is exactly one place where ad policy lives.

### How the window data is protected

The 30-day and All Time ranking windows are enforced by delivery, not by the interface. Their artefacts are not published under `public/data/`, and the repository does not commit them. The refresh uploads them to Firestore, whose security rules allow a read to a signed-in user with an active entitlement. An entitlement is the Firestore document `entitlements/{uid}` with `premium: true` and an optional `expiresAt`; only the Admin SDK writes it. `loadWindowArtefact` in `src/app/meta-window.ts` fetches the public windows as before and sends the two premium windows through `loadPremiumArtefact` in `src/app/premium-data.ts`, which loads the Firestore data only at that point, so free pages never download it. If a read is denied even after a forced token refresh, the window selector falls back to the default window. The upload and rollback steps are in the [publish premium data guide](../how-to/publish-premium-data.md).

The same rules now cover the depth of the 10-day and 20-day windows. The public `matchup-data` and `meta-share` files for those windows hold full rows and movement fields only for the top 10 decks, ranked by Power Score through `freeDeckNames` in `src/app/free-tier.ts`. Every other deck keeps its `Total` matchup row, its meta share and its game count, and nothing more. The untrimmed versions are premium artefacts in Firestore. A premium viewer reads them for every window; everyone else reads the trimmed public files, and a premium read that is denied on 10d or 20d falls back to the public file without leaving the window. While premium status is still unknown the public file is used, then the full one replaces it. Nothing on the interface is blurred any more: what a free visitor cannot see is simply not in the data they receive. The runbook describes the trimming and the publishing order in the [publish premium data guide](../how-to/publish-premium-data.md).

## How premium status resolves

`useIsPremium()` returns three states. It is `null` while authentication is loading or the entitlement lookup is in flight, then resolves to `true` or `false`. A signed-out visitor resolves to `false` immediately and loads no Firestore code. A signed-in visitor is premium when their own `entitlements/{uid}` document has `premium == true` and no `expiresAt`, or an expiry in the future. An error or a missing document does not grant access.

Downstream, `null` means "unknown", not "no". Ads stay hidden until premium status has resolved, so a Premium user never watches an ad appear and then vanish. The same applies to the gated statistics views and to the Premium panel itself, which renders nothing while status is unknown.

## How Premium access is granted

Users can send optional tips through [Ko-fi](https://ko-fi.com/dalin). Each whole GBP 1 grants one calendar month, and later tips extend the existing expiry. After signing in with Google, a user can open the Premium popup from the account menu. For a signed-in account without lifetime access, the popup leads with a Ko-fi call to action and the Google account email to use at checkout, so the Worker can match the tip automatically. A code for paying from a different email is an optional backup in a collapsed section. The popup is available to signed-in free users independently of ad consent. Lifetime access does not need a code. Owners can also grant or revoke access by hand with `yarn grant:premium`; the publishing guide covers both methods.

The popup shows the current access state and expiry, links to Ko-fi, and gives a contact address for refunds or unmatched payments. It does not create entitlements in the browser. The Ko-fi Worker or an administrator writes the entitlement using trusted server credentials.

The Firestore rules may still contain the legacy `stripeRole` condition in their `premiumData` read helper. That branch is left unchanged in the console until the owner chooses to remove it. The current app checks entitlements only, so a legacy claim alone does not enable the Premium interface.

## The ads layer

Placements are declared once in `adsConfig.ts` under `ADSENSE_SLOTS`: `anchor`, `landing`, `tierList`, `deck` and `statistics`. Every position renders through `AdSlot`, which reads the config and the shared ad state. Swapping ad networks would touch `adsense.ts`, `AdSlot` and the config file, not the pages that host the units.

Loading is lazy and consent-first. `ensureAdSenseScript()` injects the AdSense loader the first time a real slot renders, and since a slot only renders after `showAds` turns true, the script never loads before the visitor has consented to marketing. In production the consent requirement comes straight from `useConsentManager().has("marketing")`; development skips it and shows a labelled dashed placeholder instead, so layout work needs no third-party scripts. Once loaded, each `<ins>` element is keyed by route pathname, so client-side navigation remounts it and requests a fresh ad, mirroring a normal pageview for AdSense's benefit. One gap is deliberate: the `statistics` slot ID is still an empty string, so that position falls back to the placeholder even in production until an ad unit ID is filled in.

Ad-blocker detection is a single probe, and it only runs for visitors who would see real ads. `AdBlockerNotice` passes `useAdsState().useReal` to `useAdBlocked(enabled)`, which sends a `no-cors` `HEAD` request to the AdSense URL. The request cannot execute code, so the AdSense script never runs during the check. Only a rejected request counts as blocked; a request still pending after 2.5 seconds counts as not blocked. The probe runs at most once per page load, so later enables reuse the result. The hook stays `false` until the probe settles, and it does nothing while `enabled` is false.

The ContentReady handshake exists because AdSense policy forbids ads on screens without publisher content, and an SPA spends real time on screens that have none: loading spinners, error states, empty results. Each page calls `useMarkContentReady()` once meaningful content has rendered, passing `false` again whenever it drops back to a loading, error or empty view. Ads stay off on error and empty screens. For data-driven routes, a separate settled signal sets `data-route-ready` for prerendering on success, error or empty results; only rendered rows enable ads. `ContentReadyContext` stores the path that marked itself ready and compares it against the current pathname, so navigation resets readiness automatically without an effect that could race the next page's own marking. Pages that never become ready simply never show ads, and global units such as the anchor bar disappear while the current route sits in a content-less state. Slots also reserve their height up front. The anchor bar has a fixed height from `adsConfig.ts`, so an ad filling its slot cannot move the page. Its space is published as the `--ad-anchor-h` CSS variable. On mobile, `index.html` sets a default reservation before the app mounts, except while a consent banner is pending. The `data-consent-pending` attribute is removed once consent settles, or, if a popup is open then, when the last popup closes; the mobile reservation and the popup's phone layout both follow it. The anchor resets the variable to zero when it is dismissed, hidden, or blocked by an ad blocker.

## The consent layer

Consent runs on c15t. `ConsentProvider` in `src/consent/` wraps the app in `ConsentManagerProvider` (offline mode) and registers the same Google tag twice, once under the `measurement` category and once under `marketing`. c15t injects gtag with Consent Mode v2 denied by default and updates on the visitor's choice, so accepting marketing is what unlocks personalised ad signals. AdSense itself loads through the separate path described above, so the premium and readiness gates keep applying even after consent is granted.

The styling story is a cascade dispute. c15t ships its component styles inside a CSS `@layer`, and unlayered styles beat layered ones at any specificity. The app's own globals, set by styled-components at the document level, are unlayered: a 10px root font size, `button { background: none }`, `* { padding: 0 }`. Left alone, the layered c15t defaults lose every collision and the banner renders cramped and flattened. There are two responses. `consent-theme.ts` restyles the banner through c15t's supported tokens and slots wherever possible: colours, typography, spacing, button modes, the glass card background. Whatever tokens cannot express falls to `consent-overrides.css`, which is deliberately left unlayered so it wins the same cascade fight the app globals started. It targets c15t's stable class prefixes (`c15t-ui-card`, `c15t-ui-button`, and so on) and `data-testid` attributes rather than incidental selectors, because those hooks survive upstream changes. The file's own header sets the boundary: colour, fill and button treatment belong in the theme file, overrides only handle what tokens genuinely cannot.

`ConsentProvider` mounts two c15t components, not one. `ConsentBanner` is only the first surface: its Customize button does nothing but set the store's `activeUI` to `dialog`, which hides the banner and hands over to `ConsentDialog`, the modal holding the per-category switches. Mounting the banner alone makes Customize read as a broken close button — the banner vanishes and nothing replaces it — so the two always travel together, and the prerender guard skips both.

Two overrides are worth knowing about beyond looks. The banner is fixed to the bottom of the viewport, the same strip the sticky anchor bar occupies on mobile, and it is portaled to `document.body` while the anchor lives inside `#root`. The override sheet lifts the banner by `--ad-anchor-h` and pins its z-index to the maximum, so its buttons never hide under the ad bar and stacking-context comparisons between the two trees cannot bury it. The lift is scoped to the banner's own root by `data-testid`, because the dialog and the category switches share the same class prefix and the dialog's overlay has to stay pinned to the full viewport. The dialog needs its own override for a different reason: its card is centred with `margin: 0 auto`, which the app's unlayered `* { margin: 0 }` reset flattens, so the sheet hands that auto margin back. Its z-index needs no help; c15t ships the dialog at a value the anchor bar cannot reach.

The dialog's interior needed a third pass. c15t sizes the category widget in `rem` against an assumed 16px root, so at this app's 10px root the switches, arrows and gaps all render at 62.5% of their intended size, and the global `* { font-size: 10px }` flattens the accordion labels on top of that. The banner never showed the problem because the override rules above already restate its sizes. Rather than another round of per-element `!important`, the sheet restates c15t's own component variables (`--switch-*`, `--consent-widget-accordion-icon-size`, `--consent-dialog-max-width`) at the app's scale, which is c15t's value multiplied by 1.6. The switch variables have to be set on the switch root itself: c15t declares them there too, and a value set on an element beats one inherited from an ancestor whatever the layer says.

Finally, the prerender guard. The postbuild step renders routes to static HTML with a browser whose user agent is `prerender-routes`. During that run, c15t portals the banner to `document.body`, outside the `#root` mount point. The live client boots with `createRoot`, which does not adopt pre-existing DOM, so a banner baked into the static HTML would survive as a second, handler-less copy frozen on screen; for a returning visitor who had already stored a consent choice, it would be the only copy, and Accept and Reject would silently do nothing. `ConsentProvider` checks the user agent and renders no banner at all while the prerenderer drives the page, keeping dead markup out of the static HTML. Real visitors still get the banner from the live client.
