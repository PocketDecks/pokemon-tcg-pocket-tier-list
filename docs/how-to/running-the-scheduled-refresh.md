# How to run the scheduled refresh

The scheduled refresh runs `yarn refresh:job` from `analysis/`. The script follows the numbered steps below in order and stops at the first non-zero exit. It finds the canonical remote by its GitHub URL, checks the dated branch for human commits, copies `analysis/data/` to a dated backup when store verification fails, reruns a thrown download once, retries a store-lock refusal once, stops with a backup when a download reports an interrupted write, treats an empty classifier result as a silent day, builds the pull request body from the files the run generated and reads the head SHA back after the push. It compares `process.version` with `.nvmrc` before the first command and needs a person when they differ, because a mismatched Node fails the ConsentProvider tests in step 8. Pass `--dry-run` to record the planned commands with a recording runner and print them without running them.

The script does not remove a lock or claim, repair the raw store, merge, or push `main`. It stops and reports those cases for a person.

## Schedule

Run on Sunday, Tuesday, Thursday, and Saturday at 21:00 UTC.

## After the job

Report the current check states on the pull request yourself. The job does not query them.

## Prerequisite

This job publishes premium data to Firestore, so the analysis machine needs Application Default Credentials for the project before step 10 runs. The publisher identifies the canonical Git remote by its GitHub repository URL (`PocketDecks/pokemon-tcg-pocket-tier-list`) and uses that remote's `main` as the comparison baseline. Its local alias can vary between checkouts.

If the publish or verify step fails, report the exact refusal and stop. The published version document is written last, so readers never see a half-written version. Publishing before the merge is safe: cleanup keeps the newest five versions and protects the versions referenced by canonical `main`, the deployed version document on the site, and every open pull request targeting canonical `main`, including pull requests from forks. If any retention source cannot be read, publishing may proceed but deletes nothing, and the refusal names the source that could not be read.

The premium publication lock uses a Firestore transaction before listing existing versions. A competing run refuses and must stop with the lock details. A crash leaves the lock in place without automatic expiry. Before a person removes it, they must confirm the lock owner at the recorded host and process ID is gone; otherwise stop and report the lock.

## Steps the job runs

Run `yarn refresh:job` from `analysis/`. The script follows these steps in order and stops at the first non-zero exit. It writes a dated log for each command and ends with one JSON line holding the status, step, command, first error lines, head SHA and log path. The error lines are split on newlines, blank lines are dropped and each line is capped at 500 characters. Instruction lines such as `yarn refresh:outputs discard` come first, then the line that decided the stop (a refusal or lock message), then the last other error lines, then the last progress lines. At most five lines reach the JSON line, so it stays short; the full output stays in the dated log. The published outcome and the JSON line also carry the review URL read back from the pull request. Exit 0 means published or silent, 2 needs a person and 1 means failed.

Repository: the checked-out `pokemon-tcg-pocket-tier-list` repository.

Commands appear in their Linux form first. On Windows 11, the job runs the same commands in PowerShell with `yarn.cmd` in place of `yarn`, and `git`, `node` and `gh` keep their arguments. A step that names both forms shows the Linux command before the Windows 11 command.

1. Works in the main checkout. It may update `main` in step 1, then checks out the dated branch in step 2. Generated files in that checkout change only from step 11 onwards; before then the work happens in the scratch worktree. It runs `git diff --cached --name-only` and stops for a person with `index already holds entries` when the index holds any paths, naming those paths, before it fetches anything. It fetches `main` from the remote whose GitHub URL resolves to the canonical repository above; the remote alias can vary between checkouts. On Linux, when `main` is not checked out, it runs `git fetch <remote> refs/heads/main:refs/heads/main`, which fast-forwards local `main`. A non-fast-forward rejection stops for a person and names `main`; any other failure stops as failed. On Windows 11 the same `git` command runs in PowerShell with backslashes in any local path. When `main` is checked out, it runs `git pull --ff-only <remote> main` instead. It never checks out or resets `main`, and will stop if either command fails. Every `git` command in this job runs with `LC_ALL=C` and `LANGUAGE` unset, so Git prints the English refusals the job matches even on a machine set to another language.
2. Creates or reuses a dated branch named `automated/pipeline-update-YYYY-MM-DD` from the current `main` branch. The job fetches the remote branch and checks the local one with `git rev-parse --verify --quiet refs/heads/<branch>`. It checks out a local dated branch when that ref exists, even when the fetch prints `couldn't find remote ref`, and creates the branch with `git checkout -b` only when neither the local nor the remote branch exists. Any fetch refusal other than `couldn't find remote ref` stops the run, and the dated-branch fetch uses the same C locale so that wording appears in English. The job reuses the dated branch only when it contains no human commits: it compares the local branch and its remote counterpart with `git log --format='%h %an %s' main..<branch>` and `git log --format='%h %an %s' main..refs/remotes/<remote>/<branch>`, and treats every commit that is not reachable from canonical `main` as human unless its subject is `chore(data): refresh tier-list snapshot` and its author is the automation identity. On Windows 11 the `git log` invocations keep the same arguments in PowerShell. If any human commit is present, it stops, reports the branch and the commit list, and lets a person decide; it never resets, deletes, rebases or force-pushes that branch. It will stop if branch creation or checkout fails.
3. From `analysis/` in the main checkout, `yarn refresh:outputs begin` creates a scratch worktree at the current `HEAD` and prints its path; the job will stop if it fails. On Windows 11 the command is `yarn.cmd refresh:outputs begin`. The scratch worktree links `node_modules` and the raw store `analysis/data/`, so downloads still land in the real store. Every command from here to step 10 runs inside the scratch worktree, with its `analysis/` directory standing in for `analysis/` and its top directory for the repository root. `refresh:outputs` itself runs only from the main checkout. The job then runs `yarn sync-pairings`, or `yarn.cmd sync-pairings` on Windows 11, and will stop on a non-zero exit.
4. From `analysis/`, the job runs `yarn golden:generate`, or `yarn.cmd golden:generate` on Windows 11, and will stop on a non-zero exit.
5. Runs `yarn store:verify` from `analysis/`, or `yarn.cmd store:verify` on Windows 11, and continues only when it exits 0. It reads `processed-tournaments.json`, its staging sidecars, and every shard entry, so a batch killed between the manifest and processed-tournaments renames is reported here before any duplicate-deck refusal. If verification fails, the job stops. Before any human repair, it copies the full `analysis/data/` directory, including `decks/`, `processed-tournaments.json` and any sidecars, to `analysis/data-backup/YYYY-MM-DD/`, then asks a person to review it. Never delete or restore raw-store files automatically.
6. From `analysis/`, the job runs `yarn download`, or `yarn.cmd download` on Windows 11. The downloader commits the deck store a batch at a time, so a run that fails with a thrown error keeps the batches that finished: every deck in the store belongs to a tournament in `processed-tournaments.json`, and every tournament listed there has been processed, whether or not it produced usable decks. A run that fails with a thrown error may be rerun from those batches without duplicating a deck. A killed run can leave the shard and manifest on the new batch while `processed-tournaments.json` still holds the old one; `yarn store:verify` now reports that state and its staging sidecars. If it does, or if a rerun refuses with `Deck ... already exists in shard`, the job does not rerun again: it applies the backup-and-stop rule in step 5, reports the exact refusal, and lets a person reconcile the batch. After a killed run, `yarn refresh:outputs discard` runs from the main checkout, the next run starts at step 1, and `yarn store:verify` runs before `yarn download`. On Windows 11 these are `yarn.cmd refresh:outputs discard`, `yarn.cmd store:verify` and `yarn.cmd download`. Partial output is not a reason to stop, because the store is the resume point. The job will stop on any non-zero exit and report the exact error.
7. From `analysis/`, the job runs `yarn card-printings:generate`, then `yarn start`, with `yarn.cmd card-printings:generate` and `yarn.cmd start` on Windows 11. `yarn start` runs `assertPublishable` before writing JSON. It commits JSON atomically, then commits OG images separately; the image commit can fail after JSON publication, in which case the rendered staging directory is kept and the refusal names its exact path. The job will stop on a non-zero exit. From the scratch worktree's top directory it runs `node scripts/build-deck-archive.mjs`, `node scripts/generate-deck-hub-slugs.mjs`, then `node scripts/generate-deck-redirects.mjs`, stopping on the first failure; Windows 11 uses the same `node` commands in PowerShell. From `analysis/`, run `yarn validate:refresh` (the script exists only in `analysis/package.json`) and stop on failure; on Windows 11 the command is `yarn.cmd validate:refresh`. The job captures the `union:` line from this command for the pull request body and stops as failed when the command prints no such line.
8. Runs `yarn test` and `yarn typecheck` from `analysis/`. From the scratch worktree's top directory, it runs `yarn typecheck`, `yarn lint`, `yarn test:ci`, and `yarn check:generated`. On Windows 11 each command is the `yarn.cmd` form in the same order. The job stops at the first failure and reports the command and first error.
9. From `analysis/` in the main checkout, the job runs `yarn refresh:outputs classify`, or `yarn.cmd refresh:outputs classify` on Windows 11. It lists the output paths in the scratch worktree that differ from `HEAD`, plus premium files that differ from `analysis/out/premium/`. When the classifier prints no paths, it runs `yarn refresh:outputs discard`, will report a silent day and stop. The classifier excludes `src/app/last-updated.ts` and includes ignored premium outputs; generated hub files count as output. A run is silent only when `yarn refresh:outputs classify` prints no paths. The job never stages `analysis/data/`. It will stop on any non-zero exit and report the exact error.
10. From the scratch worktree's `analysis/`, the job runs `yarn publish:premium --dry-run`, then `yarn publish:premium`, then `yarn verify:premium`, with the `yarn.cmd` forms in the same order on Windows 11. It will stop on any non-zero exit and report the refusal.
11. Runs `yarn refresh:outputs stage` from `analysis/` in the main checkout, or `yarn.cmd refresh:outputs stage` on Windows 11. It moves the finished outputs, including the ignored premium files and snapshots, out of the scratch worktree into the checkout, runs `git add` on exactly the changed output paths, and removes the scratch worktree. Then it commits the staged outputs with `chore(data): refresh tier-list snapshot`, naming exactly the paths the stage step printed. Before that commit it runs `git diff --cached --name-only` again and stops for a person when the index holds a path the stage step did not print; the refusal names the extra paths and makes no commit. The job will stop on any non-zero exit and report the command and first error; it does not push a partial commit.
12. Pushes the dated branch to the repository's review remote and creates or updates one pull request against `main`. The title is `chore(data): refresh tier-list snapshot`. The body has the four lines that `buildPrBody` emits: tournament and deck counts, ranked archetypes for the ten, twenty, thirty and all windows, image parity from the `union:` line, and the premium data version read after `verify:premium`. It has no pairing-row counts or test results. On Windows 11 the same `git` and `gh` commands run in PowerShell. It will stop on any non-zero exit and report the command and first error. The push may already have landed, so the dated branch stays pushed and the next run reuses it.
13. Reads the pull request back after publishing. It verifies that its head SHA equals the local commit and returns the review URL in the published outcome and the JSON line. The job does not query check states. It will stop on any non-zero exit and report the command and first error; it stops and reports immediately if the head SHA differs. It never merges and never pushes `main`.

## Freshness

Windows anchor on the newest data date, so stale raw data still fills each window and ranks archetypes. Score weights use that same data anchor. The trend series includes every calendar day with qualified games, so a day's decks appear in the run that first sees them and a run with no new data stays silent. The run clock still sets `LAST_UPDATED`. `assertPublishable` compares the newest qualified deck date with the run clock and refuses data older than `MAX_DATA_AGE_DAYS`; this freshness guard is implemented in code. The gate in `yarn start` runs before the new files are written and reads the free-window baselines from the working tree; `yarn validate:refresh` runs afterwards and reads both free and premium baselines from canonical `main`. They share the floor date source, ramp, ratio and release rule, but the validator does not repeat the gate's ranked, age, unmatched-bucket, slug or listing checks. A fresh checkout has no local snapshot for the version canonical `main` serves, so both log a first publish and skip only the previous-archetype-count ratio for the 30d and all windows; the configured floors still apply. `publish:premium` writes that snapshot.

## Recovery

Generation happens in the scratch worktree, so a failed or killed run leaves generated files there. Step 1 may update `main`, and step 2 leaves the dated branch checked out in the main checkout; generated files reach that checkout only from step 11. Confirm no refresh is running, then run `yarn refresh:outputs discard` from `analysis/` in the main checkout and start again at step 1. On Windows 11 use `yarn.cmd refresh:outputs discard`.

- `begin` refuses because the scratch worktree exists: another refresh is running, or an earlier one was killed. This is the guard against two refreshes at once. If none is running, discard and start again.
- `begin` or `stage` refuses with `generated outputs already changed in the working tree`: someone edited a generated output in the main checkout. Report the paths and let a person decide; do not discard the edit to make the run pass.
- Step 1 refuses with `index already holds entries`: the index held paths before the run started. It names those paths and makes no commit. Unstage them yourself, then start again at step 1; do not stage them with the refresh.
- Step 11 refuses with `index has entries outside generated paths`: stage has already moved the outputs into the checkout and removed the scratch worktree, so unstaging only the extra paths leaves the outputs staged and the next run stops at step 1 again. Follow the step 11 restore procedure below, then unstage the extra paths and start again at step 1.
- A kill during step 11, while outputs are being moved, can leave some outputs replaced, deleted or newly added in the main checkout. Do not use the `classify` list for this: it leaves out `src/app/last-updated.ts`. `yarn refresh:outputs outputs` prints every tracked output path, the timestamp included. Restore them all with `git restore --source=HEAD --staged --worktree -- <those paths>`. `git restore` leaves new files alone, so list them with `git ls-files --others --exclude-standard -- <those paths>` and delete only what it prints. Delete any `*.tmp` file beside them, delete `analysis/out/premium.incoming` and `analysis/out/premium-previous.incoming`, and if `analysis/out/premium.outgoing` or `analysis/out/premium-previous.outgoing` exists next to a missing `premium` or `premium-previous`, rename it back. Then discard and start again at step 1.
- A failed image swap after the JSON was written keeps `public/og/deck-stage-*` inside the scratch worktree only. Discard it and start again; the published images in the main checkout were never touched.

## Failure rules

- Do not publish raw tournament data.
- Do not treat a failed download as a finished one. A run that failed with a thrown error keeps the completed batches and may be rerun once. A killed run needs the discard in the Recovery section, so start a new run at step 1 and run `yarn store:verify` before `yarn download`. If store:verify reports an interrupted processed-tournaments batch, or a rerun refuses with `Deck ... already exists in shard`, stop, back up `analysis/data/` as step 5 requires, and ask a person to reconcile it; a blind rerun cannot fix that state.
- A download refused by the store lock may be retried once, after a few seconds, if the refusal says to retry. Any other refusal is stopped and reported, naming the holding pid, the claim file, or the lock file. A later run reclaims a lock or claim whose owner has gone. The exception is a claim or lock whose pid has been reused by an unrelated process: it still looks held and needs deleting by hand, which this job must not do, so stop and report it.
- Do not override a refusal from `yarn start`. Report the failures it prints.
- Do not open a second review for the same dated branch.
- A run is silent only when `yarn refresh:outputs classify` prints no paths. The classifier excludes `src/app/last-updated.ts` and counts ignored premium outputs.
