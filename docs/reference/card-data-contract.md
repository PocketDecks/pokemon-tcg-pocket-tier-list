# Card data reference

The frontend reads card data from the `pokemon-tcg-pocket-cards` npm package,
resolved through its typed `core` export. That file is a sparse
projection: Trainers omit `ex`, `health` and `stage`, and `normaliseCard` coerces
those fields back. Attack costs instead come from `src/data/attack-costs.json`,
which `scripts/generate-attack-costs.mjs` builds at prebuild from
`data/v5/cards.gameplay.no-image`. The field names in the payload differ from the
ones the app uses, so everything passes through a normalisation layer first

## Where normalisation happens

`src/app/cards-api.ts` owns the contract. `fetchCards()` is the only function
that should read the card payload. It maps each record through
`normaliseCard` and returns `CardType[]`. Both `DecksContext` and `useCards`
call it under the same `["cards"]` query key. The attack index consumed by
`fetchCards` is generated from the gameplay projection at prebuild, so the
frontend never imports the 1.19 MiB payload.

## Field mapping

| Payload field | App field | Notes |
| --- | --- | --- |
| `set_code` | `set` | Lower case, for example `a1`, `b4`, `pa`, `pb`. |
| `subtype` | `type` | Elemental type for Pokémon, class for Trainers. |
| `type` | `supertype` | Either `Pokémon` or `Trainer`. |
| `ex` | `ex` | Boolean, not the string `"Yes"` or `"No"`. |
| `id`, `name`, `rarity`, `pack`, `health`, `stage`, `image` | unchanged | |

`RawCardType` aliases the package's generated core schema. `CardType` describes
what the rest of the app sees. Neither carries `craftingCost`, which appears in
no payload record

## Field values

`supertype` has two values: `Pokémon` and `Trainer`.

`type` carries ten elemental types for Pokémon: Grass, Fire, Water, Lightning,
Psychic, Fighting, Darkness, Metal, Dragon and Colorless. These match the
`ENERGY_TYPES` list in `TierListPage` exactly, so the energy filter compares
them directly. For Trainers, `type` is one of Item, Supporter, Tool or Stadium.

Because a Trainer's `type` holds a class rather than an element, filters that
ask about elements must test `supertype === "Trainer"` first.

## Deck list format

Deck lists store each card as `"<count>:<id>"`, for example `"2:a1-001"`. A
deck name ends in the id of each icon card, joined by `&` for a two-Pokémon
deck, as in `venusaur-a1-004&bulbasaur-a1-001`. `src/app/deck-filters.ts` holds
the parsers for both formats.

## Filter predicates

`src/app/deck-filters.ts` exports the deck list predicates as pure functions.

| Function | Returns false when |
| --- | --- |
| `isAffordable` | The list needs more copies of a card than the user still has. |
| `matchesEnergy` | A Pokémon in the list is not the selected element. Trainers always pass. |
| `matchesExFilter` | The list holds an ex Pokémon and ex cards are excluded. |
| `hasEnoughLatestExpansionCards` | The list holds fewer cards from the newest set than required. |
| `findUnresolvedCardIds` | Not a predicate. Returns the ids absent from the card data. |

Every one of them takes the list's `"<count>:<id>"` entries as its first
argument, so none of them needs React. What follows differs: `matchesEnergy`,
`matchesExFilter` and `hasEnoughLatestExpansionCards` take the id-to-card index
and the filter value, `findUnresolvedCardIds` takes only the index, and
`isAffordable` takes neither, working from the user's missing counts instead.

## Drift between the two data sources

The card data resolves from the `pokemon-tcg-pocket-cards` package, while the
deck lists in `public/data/` are regenerated by the analysis pipeline. A card id
can therefore appear in a deck list without existing in the card data.

`DecksContext` resolves this before any other filter runs. Lists holding an
unresolvable id are dropped, decks whose icon card is missing are dropped, and
every skipped id is reported in one `console.warn` per render. `useCards` skips
unresolvable scored cards and warns the same way.

Because the failure is now quiet, that warning is the signal that the installed
package has fallen behind the live meta. Updating the dependency is the fix.
